# Leona Android V1 identity foundation

Status: `CANDIDATE_ONLY` / support evidence. This document does not claim
device or backend runtime acceptance.

## Scope and authority

The Android SDK collects and reports evidence. It does not decide allow/deny,
block, or risk. The customer backend owns authorization scope and the final
verdict. `tenant`, `app`, and optional `environment` labels are routing
context only: they are encoded inside the caller-owned protected request
context and are not crypto-scope commitments or client authorization
authority.

No customer package/class/JNI name, hardware identifier, raw serial, IMEI, MAC,
secret, token, or fixed private key is used to create identity.

The optional `environment` label is routing context only. It is trimmed, must
be at most 64 characters, and rejects control characters. Invalid labels are
rejected rather than truncated, so the protected request cannot silently
disagree with the caller's configured value; the label is never an
authorization scope or client-side verdict input.

## V1 lifecycle contract

### `install_id`

* A fresh installation gets a cryptographically random UUID generated by the
  SDK. It is not derived from hardware, package timestamps, or a device model.
* The encrypted Android Keystore envelope is stable across process death,
  reboot, and an app upgrade. Clear-data and uninstall/reinstall naturally
  create a new value.
* A server-issued `I` value may replace the provisional UUID only through the
  existing strict response admission rule. It remains a correlation handle,
  not canonical device identity or a business verdict.
* Every replacement writes the encrypted install record and removes the cached
  snapshot in one synchronous preferences transaction; a failed commit leaves
  the previous install/snapshot pair intact.
* The local value is never placed in a cleartext HTTP header. Public request
  metadata uses a SHA-256 handle; the raw value can appear only in a
  caller-owned protected context.

### `session_id`

* A fresh random `S`-prefixed value is generated for every SDK/process
  initialization. It is intentionally separate from `install_id`.
* It is memory-only and never persisted as install state. A process restart or
  a second process therefore gets a different session value while retaining
  the same install value when Keystore storage is available.
* Request metadata carries only a SHA-256 handle. Diagnostics redact the value
  by default.

### Keystore failure and corruption

The store never falls back to a fixed plaintext secret. If Android Keystore is
unavailable, API support is below the floor, or an authenticated envelope is
invalid, the SDK emits a typed `IdentityProtectionStatus` with a bounded code.
The collector may use a process-memory-only random install handle so evidence
collection remains explicit and non-authoritative; the status is reported as
`EPHEMERAL_MEMORY_ONLY`/`KEYSTORE_UNAVAILABLE` (or `UNSUPPORTED_API`). A
caller must not promote that state to an authorization decision.
Degraded snapshots are returned to the protected evidence channel but are not
written to the durable identity cache; failures remain visible through the
typed status rather than being swallowed as a healthy state.

If the snapshot envelope or authenticated snapshot JSON is malformed, the SDK
removes only that invalid snapshot record synchronously and preserves the
corruption status on the current report. If the clear fails, the status is
`CORRUPT_OR_MISSING` with `STORAGE_WRITE_FAILED`, `durable=false`, and
`recoverable=true`; the next resolution retries the same clear operation. Once
the clear succeeds, the following resolution consumes the one-shot corruption
status and can write a fresh encrypted snapshot; the report that observed the
corruption remains degraded.

### Protected transport boundary

Identity additions such as `session_id`, protection status, environment, and
the install-lifecycle hint are **Leo protected logical fields**. They are
assembled into the logical header map consumed by
`LeonaCryptoProtectedHeadersCodec` and are not emitted as clear HTTP headers.
The outer request contains only the Leo encrypted envelope. Exact Android ↔
Leo Provider ↔ API/Rust field mapping is `CROSS_MODULE_BLOCKED` /
`NOT_ADMITTED` until the provider contract and evidence are frozen; this SDK
does not guess that wire mapping or provide a plaintext fallback.

Each encrypted identity record now carries a version and record-domain label
authenticated as AES-GCM AAD. Existing v1 envelopes are accepted only after
strict record-shape and plaintext semantic validation, then synchronously
migrated to the v2 domain-bound envelope without rotating a valid value.
Install, canonical, and snapshot records are quarantined independently so a
single malformed record cannot delete unrelated evidence. Keystore failures
leave recoverable ciphertext untouched.

## Android 6–16 compatibility contract

The SDK V1 candidate targets API 23 through API 36 (Android 6.0 through
Android 16), with the following matrix dimensions:

| Dimension | Contract |
| --- | --- |
| SDK compile/target | compile SDK 36; sample target SDK 36 |
| SDK/sample minimum | min SDK 23 (Android 6.0) |
| Native ABIs | `arm64-v8a`, `armeabi-v7a`, `x86_64` |
| Build modes | debug, release, release with R8/minification |
| Process/lifecycle | single-process candidate; first install, warm/cold restart, upgrade, clear-data, uninstall/reinstall |
| Evidence role | collect/report evidence only; backend owns verdict |

The machine-readable source of truth is
`compatibility/android-6-16-contract.json`. Build success is not runtime
acceptance; matrix runtime evidence must remain redacted, direct, immutable,
and same-APK verified for each API cell.

Multi-process use is currently `BLOCKED_NOT_ADMITTED`: the implementation uses
process-local synchronization and Android `SharedPreferences`, which do not
prove a cross-process single-writer or coherent read contract. A future
multi-process admission requires a real atomic store and dedicated evidence;
the SDK must not imply support by relying on `@Synchronized`.

### Crypto adapter boundary

`crypto-adapter` currently declares `minSdk = 24`. Therefore API 23 can build
the base SDK identity lane but cannot claim a working crypto-adapter/provider
lane. API 23 is explicitly **blocked until a formal Provider/API23 contract
and evidence exist** (`CRYPTO_PROVIDER_API23_EVIDENCE_MISSING`). Do not lower
the adapter minimum or add a plaintext/legacy transport fallback to make the
matrix appear green.

## Privacy field registration

`IdentityFieldRegistryV1` is the code-level registration table. Every entry
records source, API range, permissions, purpose, stability, distinctiveness,
spoofability, privacy level, default switch, protection, retention, and
missing-data strategy. The registry is metadata and does not authorize
collection or make a verdict. Policy may disable optional fields; missing
fields remain explicit rather than being replaced with hardware identifiers.

The collector deliberately excludes hardware IDs and raw network identifiers.
Android ID is app/user scoped, optional, and used as a local hash input plus
encrypted snapshot evidence;
it is not emitted raw in the secure network payload. The default diagnostic
view is redacted, while an explicit `FULL_DEBUG` export is a caller-authorized
local diagnostic that may expose raw local fields such as Android ID or
install ID; that view is not wire admission or server authorization evidence.
